# Open Questions

See [`AUDIT_INDEX.md`](AUDIT_INDEX.md) for the evidence-level legend. These are questions this audit could not resolve from available evidence (code, tests, or on-disk artifacts) and that require either further runtime inspection this audit's tooling couldn't perform, or an actual product/research decision from a human.

## Research design

1. **Was the quadratics-only research design in `docs/research-design.md` deliberately superseded when the RISE bank was adopted for the adaptive condition, or is the contradiction (Finding F-02) an unaddressed gap?** `docs/research-decisions.md` RD-0001/RD-0002/RD-0008 explain the engineering reasoning for adopting RISE, but none of them revisit or amend `docs/research-design.md`'s own "two conditions share the same question bank... session structure" statement, and that document's own "Mathematics domain" section still reads "Quadratic Equations and Quadratic Functions" only. This audit found no evidence either way of an intentional, reasoned decision to broaden the comparison's scope — only that it happened as a side effect of three separate, locally-justified engineering decisions.
2. **If the two conditions are meant to be compared at all going forward, on what question bank?** The original, narrower, more-rigorously-authored bank; the broader, not-independently-reviewed RISE bank, re-scoped to a non-adaptive equivalent; or is a formal cross-condition comparison no longer the near-term goal, with the adaptive product's RISE-bank buildout now the primary deliverable in its own right? This audit cannot answer this from code alone — it is a product/research decision.

## Adaptive engine and UI

3. **Is `/adaptive-tutor`'s continued, unlinked-but-live existence intentional** (a stable, minimal reference implementation kept deliberately separate from `/practice`'s evolving feature set) **or is it meant to be retired/redirected now that `/practice` supersedes it?** This audit found no documentation stating either intent. If it is meant to stay live, Finding F-01 (the continuity-fix gap) should be fixed there too; if it is meant to be retired, the gap becomes moot but the page, its tests, and its "Adaptive Tutor" nav entry are otherwise live, functional code that would need an explicit decision to remove.
4. **Should `Question.difficulty` (or a session-held "previous question's difficulty") be threaded into `explainSelection` so "Moving to a harder question" (Finding F-06) can be made to mean what it says?** This is implementable without touching the protected Phase 3/4 algorithms (the explanation layer already sits outside them) — this audit did not attempt it, since the task scope was diagnostic only, but flags it as a low-effort, well-scoped fix if desired.
5. **Does any prerequisite edge in `data/question-bank/prerequisite-edges-v1.csv` cross from a low-`curriculumLevel` CH01 concept into a much later chapter (e.g., CH13, Permutations and Combinations)?** This would materially affect how Investigation C (`ADAPTIVE_ENGINE_DIAGNOSTICS.md` §7) explains the reported "counting" question in the referenced 20-question demonstration session. This audit did not exhaustively trace the 204-edge prerequisite graph for cross-chapter edges; doing so would resolve this specific HYPOTHESIS into either SOURCE VERIFIED or ruled out.

## Persistence and data integrity

6. **Is a true "reset all my adaptive data" control (covering `rise-student-mastery-state-v1` and `rise-student-question-history-v1`, not just `rise-student-history-v1`) wanted in the Settings page?** Currently no UI path clears the two new keys at all (Finding F-04). This is a product decision (should a student even be able to fully reset their estimated mastery?) as much as an implementation gap.
7. **Should the Dashboard/Progress "current mastery" view be switched to read from the new, authoritative `rise-student-mastery-state-v1` store instead of re-deriving it from `rise-student-history-v1`'s per-session snapshots** (Finding F-04), now that the former exists and is more precise? This audit did not attempt this change (diagnostic-only scope) but notes it as the natural resolution to the two-stores inconsistency.

## Research pipeline

8. **Is the Phase 8 confirmatory-execution block (`protocol/APPROVAL.md`'s absence) enforced as a hard, code-level gate inside `src/research/phase8/pipeline/`, or does the pipeline simply have no valid approved configuration to execute against today?** The Experiment Designer page's own copy claims the former ("blocked at the execution layer... not merely a disabled button"); this audit read that claim and confirmed the file's absence, but did not trace every code path in the pipeline module to independently verify the enforcement mechanism itself. Resolving this would require either reading `src/research/phase8/pipeline/` end to end for an explicit approval check, or (out of scope for a read-only audit) attempting a confirmatory invocation without an approval file and observing whether it is actually refused in code.
9. **Is there a plan to wire Phase 6's artifact/export/integrity system into the Phase 8 Track A/B runners (C11)?** Both systems exist and are independently tested; only the integration between them is missing. No roadmap document this audit read commits to a timeline for this.
10. **Is a BKT-based condition (C4) intended to be formally registered in `src/research/experiment/conditions.ts`,** now that real BKT estimators exist under `src/research/phase8/estimators/`? Currently the Phase 8 BKT work and the Phase 5 condition registry are two separate, unconnected implementations of "an estimator," and only the Phase 5 registry is what a live adaptive session could theoretically use.
